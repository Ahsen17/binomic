# 技术债务

这里记录框架有意接受的能力缺口：每一项都是评审后的裁决——机制缺口真实，但
当前不实现。每条记录给出裁决时间、缺口描述、依据与重议条件；路线图中标记
「裁决不做」的条目指向本页。

## 投递侧速率上限

**2026 年 10 月裁决：不实现。**

路线图曾把「投递侧速率上限」（单位时间投递数上限）列为计划项。

缺口描述：投递速率与既有两个配置维度正交——`capacity` 约束存量（未确认总数），
`concurrency` 约束执行并发度。当消费速度不低于投递速度时，队列深度持续低于
`capacity` 上限，容量检查永不触发；此时下游承受的执行速率上界约为 `concurrency`
除以单次任务时长，任务越快上界越高，框架层对此没有约束。

裁决依据：

- 缺少场景驱动：裁决时没有出现「需要限制投递速率」的实际负载或使用者诉求；
- 行业先例没有可直接照搬的口径：Celery 的任务级 `rate_limit` 按 worker 实例
  各自生效，不是全局口径；dramatiq 提供的是 Redis 支撑的分布式原语，由使用者
  在任务内自行组合；arq 没有内置速率限制；Google Cloud Tasks 的队列级
  `max_dispatches_per_second`（令牌桶）与投递侧限速最接近，但超限行为是延迟
  排队而非拒绝。

控制面因此保持 `capacity`（存量上限）与 `concurrency`（执行并发度）两个维度。

重议条件：出现真实场景——典型如任务调用 QPS 受限的外部服务、需要约束下游
承受的速率——时重新做必要性论证；届时需一并裁决作用位置（投递侧或执行侧）、
计数口径（单进程或 Redis 全局）与超限行为（拒绝或延迟排队）。

## DLQ 记录的死亡原因字段

**2026 年 11 月裁决：暂不实现。**

DLQ 运维工具链（`dlq_depth` / `dlq_list` / `dlq_read` / `dlq_replay` /
`dlq_prune` 与保留策略）落地时评审了「把死亡原因写入 DLQ 记录」：死亡原因
（`timeout` / `expired` / `max_attempts`）在 Worker 调用 `dead()` 时已知，但
持久化它需要扩展 `_DEAD` 脚本、`Broker.dead` 签名与 `WorkerHandler` 调用点。

裁决依据：

- `on_dead` 钩子已在消息进入 DLQ 时实时告知原因，事后通知链路不存在缺口；
- 检查面已覆盖「发生了什么」（任务、参数、终态 `attempt`、投递时间戳、进入
  DLQ 的时刻）；「为何死」由钩子承担；
- 保留策略按年龄清理，不需要原因字段；当前没有按原因过滤或展示的真实场景；
- 扩展点位于投递路径上的脚本与方法签名，改动风险与收益不成比例。

重议条件：出现按死亡原因过滤、展示或清理 DLQ 记录的真实场景时重新论证；届时
`_DEAD` 脚本、`Broker.dead` 签名与存量记录（无原因字段的兼容读取）需一并设计。
